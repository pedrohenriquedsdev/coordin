# Tasks — sequencing-scenarios

Regras para todas as tasks:
- **Modelo:** os grupos 1 a 4 (motor) são o caminho crítico e têm lógica sutil (aceleração sem mudar resultados, busca determinística): usar o modelo mais forte disponível. Os grupos 5 e 6 (API) copiam padrões que já existem e têm testes que pegam erro cedo: um modelo mais simples serve, com o diff revisado antes do commit. O grupo 7 volta ao modelo mais forte. **Se algo não estiver claro, pare e pergunte; não invente comportamento fora das specs nem do `design.md`.**
- **Nenhuma dependência nova** (NuGet ou npm): qualquer pacote exige pausa e a autorização do autor (`CLAUDE.md` §11). O motor continua sem dependências.
- **Não editar `docs/PRD.md` nem `docs/TDD.md`** durante a implementação: os ajustes do TDD (D12 do `design.md`) são propostos ao autor na task 7.2, e só são feitos com a aprovação dele.
- Padrões a copiar: motor (`Coordin.Engine/Forecasting/*`, `Planning/*`, `Capacity/*`; testes em `tests/Coordin.Engine.Tests/*`, `PlanningSnapshotBuilder`, `RandomPlanningGenerator`, `Day`); API (`Features/Demands/*`, `Features/Planning/*` com `PlanningTransaction`, `ScheduleEndpoints`; testes em `tests/Coordin.Api.Tests/Demands/*`, `Planning/*`, `Http/DemandPlanningContractTests.cs`, `PlanningTestData`).
- Comentários XML e textos ao usuário em português (pt-BR); identificadores em inglês. Datas de calendário: `DateOnly` no .NET e texto `yyyy-MM-dd` na API, nunca `DateTime`. O motor não usa `DateTime`, `TimeZoneInfo`, `Random` nem `Guid.NewGuid` (um teste varre o código); o `CancellationToken` é permitido.
- Ao fim de cada grupo, rode os comandos do escopo e mantenha tudo verde: `dotnet build Coordin.slnx` (0 avisos), `dotnet format Coordin.slnx --verify-no-changes` (se falhar, `dotnet format Coordin.slnx`) e `dotnet test Coordin.slnx` (com o Docker aberto, para os testes de API). O autor recebe **uma** lista de comandos de commit por grupo, com as marcações deste `tasks.md` dentro do commit do código. Cada commit compila e passa nos testes sozinho.
- Nenhum dado real ou segredo no repositório, nem nos testes. Verificações manuais com credenciais usam banco descartável e só rodam com a autorização do autor.
- Lições a lembrar (`CLAUDE.md` §13): o analisador exige chaves em todo `for`/`if` (IDE0011); `record` com lista compara por referência, então compare serializado ou com `SequenceEqual`; para testar restrições do banco, use SQL direto (o *change tracker* do EF recusa antes); uma requisição de escrita sem corpo responde `404` em vez de `401`, então teste de contrato envia corpo; testes de API não devem apagar dados das outras classes (use títulos e ids próprios); o gerador do cliente precisa de `--ignoreUnusedModels false`, de restaurar `api-configuration.ts` e de converter a pasta `api` para LF; uma dependência **pode** antecipar uma demanda sem relação.
