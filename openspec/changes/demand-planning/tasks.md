# Tasks — demand-planning

Regras para todas as tasks:
- **Quem implementa pode ser um modelo mais simples: siga o texto de cada task à risca, copiando o padrão do arquivo indicado.** Se algo não estiver claro, pare e pergunte; não invente comportamento fora das specs.
- Nenhum pacote novo (NuGet ou npm). O motor `Coordin.Engine` **não muda**. Se surgir a necessidade de instalar algo, a task pausa e pede a autorização do autor (`CLAUDE.md` §11).
- Padrões a copiar: entidade e configuração de `Features/Teams` e `Features/Calendar`; endpoints de `Features/Teams/TeamEndpoints.cs`; contratos de `TeamContracts.cs` e `CalendarContracts.cs`; erros com `ApiProblems.Conflict(code, detail)` e `ApiProblems.InvalidField(field, message)`; testes de `tests/Coordin.Api.Tests/Teams/TeamEndpointsTests.cs` (fábrica `TestingApiFactory`, cliente autenticado `CreateAuthenticatedClientAsync`, auxiliares de `Infrastructure/RegistryTestData.cs`); testes de banco de `Persistence/CapacityRegistrySchemaTests.cs`.
- Comentários XML e mensagens ao usuário em português; identificadores em inglês. Datas de calendário são `DateOnly` (nunca `DateTime`); campo obrigatório de data no corpo é `DateOnly?` com `[Required]`.
- Cada classe de teste usa um banco próprio, mas os testes **da mesma classe compartilham o banco**: nunca presuma que só existem os seus dados; consulte pelos seus `id`s. Testes que dependem de ter só as próprias demandas (ordem, cronograma) chamam `PlanningTestData.ClearDemandsAsync` no início (task 3.1).
- Ao fim de cada grupo, o build e os testes (novos e antigos) passam, e o autor recebe **uma** lista de comandos de commit: **um commit por grupo**, com as marcações deste `tasks.md` dentro do commit do código a que se referem. Cada commit compila e passa nos testes sozinho.
